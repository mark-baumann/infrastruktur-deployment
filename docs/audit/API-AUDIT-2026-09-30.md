# API/Fleet-Audit — 2026-09-30 (AUG-GITHUB-ENGINEER)

## Befunde

### B1: spam-klassifikation Deploy rot — "no such service"
- Runs #15–#18 (2026-09-27/28) alle `deploy / deploy` failure.
- Log: `docker compose pull "spam-klassifikation"` → **`no such service: spam-klassifikation`**.
- Ursache: `service_key('Spam-Klassifikation')` → Domain-Ableitung `spam-klassifikation` … aber im gerenderten `docker-compose.yml` fehlt der Service komplett, weil **`expose: false`** (Workflow-Präsupposition "kein Streamlit-UI") → `render_configs.py` überspringt UI-Services mit `expose: false` (Zeile 138–140). Der Deploy-Job im App-Repo feuert trotzdem bei jedem Push/dispatch.
- Zusatz: `TUNNEL_TOKEN`/`OLLAMA_API_KEY` kommen als leer an (Repo-Secrets: 0), da `secrets: inherit` nur aus dem Caller-Repo erbt — beide existieren nur zentral in `infrastruktur-deployment`.
- Fix-Optionen (a) Service in services.yaml mit `expose: true` + Domain, (b) `deploy.yml` in spam-klassifikation deaktivieren, solange `expose:false`, (c) build-deploy.yml um `deploy_disabled`-Input erweitern.
- Der `expose:false`+`type:ui`-Pfad generiert auch **keinen** compose-Eintrag — nach CICD-Plan Phase 2 war das als "kein Cloudflare, aber Port+Healthcheck" intendiert. Drift zwischen Plan und Renderer.

### B2: render-configs.yml — Protected-Branch-Race
- Run 36644230391 (push 461ea5e4, 2026-09-29): Push zu `master` abgelehnt: **GH006 Protected branch update failed** (required checks `deploy / build`+`deploy / deploy` + strict).
- Der im Workflow vorgesehene Bot-Branch-Weg war im Commit cf32b0ae schon gefixt (PR-Branch+PR #21/#22), aber der Direct-Push-Zweig im `push`-Trigger des selben Workflows läuft weiter in den Hook. Aktuell: nach PR #22 ist master wieder synchron, kein Dauerschaden.
- Empfehlung: Render-Workflow nur via `workflow_dispatch` + Bot-PR laufen lassen; den `push`-Trigger mit `push-branches: [render-bot/**]` einschränken oder ganz entfernen.
